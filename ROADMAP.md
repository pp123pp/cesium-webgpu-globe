## Advanced solar visual direction

The long-term visual target is **real-time solar rendering with mature game-engine visual quality while preserving Cesium's geospatial correctness**. The staged direction, reference implementations, architecture boundaries and future acceptance principles are documented in [Solar Rendering Vision](docs/SOLAR_RENDERING_VISION.md).

M2.6.1 is the completed, bounded solar-polish implementation and technical-acceptance task (final WebGL evidence pending publication integration). B1–B5 are sequential review phases. B1 B01/B02 was visually accepted and merged through PR #21; B2 B03/B04 was visually accepted and merged through PR #22; B3 B06 HDR Bloom was visually accepted and merged through PR #23. B4 B05 Atmospheric Glow Integration was visually accepted by the user on 2026-11-04 and merged through PR #25 at `34f2571b80ee1854e4a7b8369c845aa506a0b24d`. B5 B07 static, temporal, performance and lifecycle acceptance were user-confirmed on 2026-11-04 and merged through PR #27 and PR #28. The SVP-01–SVP-10 evidence matrix is indexed in `coordination/evidence/M2.6.1/README.md`; the separately authorized complete physical-GPU WebGL differential passed on merged `main` `b5422e5` on 2026-11-05, with three unchanged baseline failures and zero new regressions; evidence publication is pending. M2.7 remains an optional future track after M5. M2.8 A/B is independently authorized after M2.6.1 (see tasks/M2.8.md), without requiring M2.7: they must not delay or become prerequisites for M3 volumetric clouds, M4 cloud lighting, M5 stabilization or V1.0. They require separate task definitions and explicit authorization before implementation. No full RenderGraph, general PBR engine or broad renderer rewrite is implied.

## Strict scope gate

M0–M6 must **not depend on** implementing 3D Tiles, general GPU material engine, complex RenderGraph or full Cesium WebGPU coverage. Add abstraction only when two real consumers prove necessity. Each milestone: vertical slice → tests → demonstration → handoff. M6 uses its own acceptance IDs and does not silently expand the original V1.0 definition.

## Task assignment protocol

Before coding: select **one** numbered bullet from `tasks/MX.md` (for M6, one task ID from the active `tasks/M6/Ox.md`), state owned files, output, acceptance test and whether it may run in parallel. If a task cannot be independently tested, split it further. Do not implement future milestones in the same PR.

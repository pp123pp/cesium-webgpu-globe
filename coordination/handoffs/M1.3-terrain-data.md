## Boundaries and known limitation

Only test-local `Resource.fetchJson/fetchArrayBuffer` and `TaskProcessor.scheduleTask` transport are adapted. Reads are constrained by canonical filesystem paths to the existing terrain fixture directory; network URLs and unexpected resource/worker types fail. The native provider decoder, three native worker message handlers, structured cloning, transfer lists and terrain classes run unchanged. Prototype/global descriptors are restored. Actual browser Worker scheduling, throttling, cancellation, network behavior and GPU drawing are outside this Node suite. The live report documents a separate earlier browser probe; this slice launched no browser/server.

Small fixtures reuse one binary for multiple coordinates and do not constitute a coherent offline terrain pyramid. The tests establish a reusable CPU mesh boundary, not A05, crack-free rendered LOD, imagery integration or completed M1 acceptance.

**Inherited post-mesh height query issue:** `QuantizedMeshTerrainData.interpolateHeight` scales query UV to 0–32767 (`packages/engine/Source/Core/QuantizedMeshTerrainData.js:544–566`), but its mesh path compares against normalized UV from `TerrainEncoding.decodeTextureCoordinates` (`:581–609`; `Core/TerrainEncoding.js:473`). Center interpolation was finite before `createMesh` and undefined afterward. The prior Everest probe observed 6142.144967542046 m before meshing and no numeric result afterward. No upstream fix is included. The test emits a diagnostic rather than declaring the undefined result a correct contract or using it as a mesh-height oracle.
